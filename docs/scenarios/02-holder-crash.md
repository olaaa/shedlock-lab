# Сценарий 2. Держатель блокировки упал

Тест: `src/test/java/io/github/olaaa/shedlocklab/scenario/Scenario2HolderCrashTest.java`.
Задача — та же выгрузка `CatalogExportJob` (блокировка `catalog-export`). Сбой для опыта: `JobFaults` — следующий запуск на реплике бросит исключение. Сроки в тестах: `lockAtMostFor` 6 секунд, `lockAtLeastFor` 3 секунды; в `application.yml` — 1 минута и 10 секунд.
Ручная проверка: `http/02-holder-crash.http` на двух репликах.

Коротко:

- **Что случилось.** Реплика взяла блокировку и умерла посреди выгрузки: `kill -9`, нехватка памяти, выключили узел. Снять блокировку некому — `finally` не выполнился.
- **Что делает ShedLock.** Ничего особенного: строка блокировки остаётся с `lock_until = locked_at + lockAtMostFor`, и до этого момента остальные реплики пропускают запуски. После — первая же реплика, у которой сработало расписание, занимает строку.
- **Цена.** `lockAtMostFor` — это сколько задача не будет выполняться после падения держателя. Короче — быстрее восстановление, но выше риск, что живая, но долгая задача потеряет блокировку (сценарий 3).
- **Исключение — не падение.** Если упала сама задача, а процесс жив, ShedLock снимает блокировку в `finally` сразу; держится она только до `locked_at + lockAtLeastFor`.

## Почему блокировка вообще освобождается

README ShedLock: «если JVM упадёт до окончания задачи, в дело вступает `lockAtMostFor`. Блокировка всегда освобождается через `lockAtMostFor`». В таблице это видно напрямую: при взятии ShedLock пишет `lock_until = now + lockAtMostFor`, а занять строку можно, только когда `lock_until <= now` (запрос — в сценарии 1). Упавшая реплика ничего не обновляет, и через `lockAtMostFor` строка становится свободной сама — по часам базы, потому что `usingDbTime()`.

`lockAtMostFor` в аннотации — это и есть срок аренды из сценария 3 [redis-patterns-lab](https://github.com/olaaa/redis-patterns-lab): там Redis удалял ключ по `PX`, здесь база перестаёт считать строку занятой после `lock_until`. Javadoc `@SchedulerLock`: «сколько держать блокировку, если машина, которая её взяла, умерла, не сняв её. Это только страховка: в обычных обстоятельствах блокировка снимается, как только задача закончилась».

## Как выбрать lockAtMostFor

README: «`lockAtMostFor` нужно задать намного больше обычного времени выполнения задачи». Две силы тянут в разные стороны:

| | `lockAtMostFor` короткий | `lockAtMostFor` длинный |
|---|---|---|
| Держатель упал | задача возобновится быстро | задача не выполняется весь срок |
| Задача шла дольше обычного | блокировку возьмёт вторая реплика, работают двое (сценарий 3) | двоих не будет |

Выгрузка раз в минуту с работой 5 секунд и `lockAtMostFor` 1 минута: после падения пропустится не больше одного запуска. Для ночной задачи на час разумен срок в несколько часов: лучше пропустить одну ночь, чем выгружать вдвоём.

## Исключение в задаче — не падение процесса

Если исключение бросила сама задача, по исходнику (`DefaultLockingTaskExecutor`) блокировка снимается в `finally`:

```java
try {
    ...
    return executeTask(task, lockConfig);
} finally {
    ...
    activeLock.unlock();
}
```

Снятие сдвигает `lock_until` к `max(locked_at + lockAtLeastFor, now)`. Тест `failedTaskReleasesLockWithoutWaitingForLockAtMostFor`: выгрузка упала через 1 секунду, и `lock_until − locked_at` = 3 секунды (`lockAtLeastFor`), а не 6 (`lockAtMostFor`).

Исключение уходит дальше: при вызове из `@Scheduled` его залогирует планировщик, следующий запуск пойдёт по расписанию.

## Что проверяют тесты

`lockOfCrashedHolderIsReleasedOnlyAfterLockAtMostFor`: «падение» — провайдер реплики A берёт блокировку `catalog-export` с теми же сроками, что у выгрузки, и не снимает её. Это ровно то, что остаётся в таблице, когда процесс умирает между `lock()` и `unlock()`. Реплика B сразу после — пропуск; затем тест вызывает выгрузку на B каждые 200 мс. В прогоне:

```text
упавшая блокировка: locked_at 00:34:23.518, lock_until 00:34:29.518, locked_by replica-a
первый запуск B:    started_at 00:34:29.685
```

Реплика B выполнила выгрузку только после `lock_until` упавшей блокировки — через 6 секунд, `lockAtMostFor`.

`failedTaskReleasesLockWithoutWaitingForLockAtMostFor`: исключение в задаче — блокировка до `locked_at + lockAtLeastFor`.

## Попробовать вручную

Две реплики, как в сценарии 1. Запустить выгрузку на 8080 и, пока она идёт 5 секунд, убить процесс реплики 8080:

```bash
curl -s -X POST localhost:8081/lab/reset
curl -s -X POST localhost:8080/lab/jobs/catalog-export & sleep 1; kill -9 <pid реплики 8080>
curl -s -X POST localhost:8081/lab/jobs/catalog-export
curl -s localhost:8081/lab/locks
```

Результат такого прогона:

```text
kill -9 реплики 8080 — через секунду после начала выгрузки
POST на 8081:          {"replica":"replica-8081","executed":false}
строка блокировки:     locked_at 00:48:10.045, lock_until 00:49:10.045, locked_by replica-8080
первый запуск на 8081: started_at 00:49:10.634
журнал:                запуск replica-8080 c started_at 00:48:10.048 и finished_at null
```

Упавшая выгрузка так и осталась незаконченной (`finished_at` пуст), а реплика 8081 выполнила выгрузку через минуту — `lockAtMostFor`, — как только `lock_until` прошёл.

Затем на 8081 включён сбой (`POST /lab/faults/fail-next-run`) и запущена выгрузка: ответ `500`, а у строки блокировки `lock_until − locked_at` = 10 секунд — `lockAtLeastFor`, а не минута.

## Что важно заметить

- Упавший держатель не снимает блокировку; её освобождает срок `lockAtMostFor`, отсчитанный по часам базы.
- `lockAtMostFor` — компромисс: сколько задача простаивает после падения против риска потерять блокировку у живой, но долгой задачи.
- Исключение в задаче — не падение: блокировка снимается в `finally` и держится лишь до `locked_at + lockAtLeastFor`.

## Как сказать на собеседовании

«Если реплика умерла с блокировкой, ShedLock её не снимает — снимать некому. Строка в таблице остаётся с `lock_until = locked_at + lockAtMostFor`, и после этого момента её займёт первая реплика, у которой сработало расписание. Поэтому `lockAtMostFor` — это одновременно страховка и время простоя после падения: ставлю его заметно больше обычного времени работы, но не бесконечным. Исключение внутри задачи — другое дело: процесс жив, блокировка снимается в `finally`».
